# Сравнение минимальной iOS: Signum и ipatool 1.2.0

Вывод: ipatool 1.2.0 — более полный основной источник минимальной iOS по конкретной сборке. Кэш и доставку результатов в интерфейс следует оставить в Signum. Это вывод из анализа кода и воспроизводимых тестов ZIP-разбора, а не замер доступности Apple на реальных аккаунтах.

## Проверка архивов

Из текущего `src-tauri/src/apple_store.rs` извлечены без изменения функции чтения диапазонов и Info.plist. Они скомпилированы с существующими reqwest/plist/flate2 и запускались против локального HTTP Range-сервера. Из upstream 1.2.0 извлечены функции ZIP-разбора; HttpClient заменён чтением диапазонов того же файла в памяти. Все тестовые архивы используют ZIP_STORED; DEFLATE, сетевой libcurl и Apple-аутентификация этим сравнением не покрываются. Валидность архивов независимо проверена Python zipfile; ZIP64 создан принудительно на маленьком файле.

| Валидный IPA, ожидается iOS 14.0 | Signum | ZIP-reader ipatool |
| --- | --- | --- |
| Обычный | 14.0 | 14.0 |
| Framework с собственной iOS 18.0 перед основным Info.plist | 14.0 | 14.0 |
| Дополнительное поле ZIP-заголовка 8192 байта | Ошибка: запись обрезана | 14.0 |
| ZIP64 EOCD | Ошибка разбора оглавления | 14.0 |

Стенд и результаты: `tmp/min-ios-comparison/run.py`, `results.json`, `signum-reader.rs`, `ipatool-reader.cpp`. Команда повторения после сборки стенда: `python tmp/min-ios-comparison/run.py`.

## Отличия реализаций

- Источник истины одинаковый: MinimumOSVersion основного Payload/*.app/Info.plist именно выбранной сборки. Оба читают диапазоны вместо загрузки всей IPA и поддерживают XML/binary plist и ZIP stored/deflate.
- В Signum ZIP64 отвергается; локальный заголовок читается с фиксированным запасом 4096 байт. ipatool поддерживает ZIP64 и отдельно читает точную длину локального заголовка и данных.
- ipatool ограничивает объём HTTP-ответов, Signum вызывает `bytes()` без такого ограничения. При этом Signum проверяет HTTP 206 на каждом диапазоне, а ipatool после начального запроса проверяет в основном длины данных: upstream тоже не без недостатков.
- Signum кэширует положительный результат по app ID + external version ID и читает до четырёх сборок параллельно, отдавая результаты в интерфейс по готовности. Это полезно сохранить. Скорость обоих вариантов на живом Apple CDN не замерялась.
- ipatool использует собственную сессию и общий для скачивания механизм получения ссылки, включая обновление KBSync и однократный повтор входа при истёкшем token. У Signum есть импорт сессии ipatool и свои резервные запросы, но остаются зависимости от состояния нативной сессии/подписывающего helper.
- Новые `minimumOSVersion` и `supportedPlatforms` из `get-version-metadata` сейчас не разбираются Signum. Поэтому данные могут уже быть получены дочерним процессом и затем запрашиваться повторно другим способом.
- В Signum лимит одной команды метаданных — 20 секунд, а диапазонный запрос upstream может ждать 60 секунд. На медленном CDN Signum способен прервать команду до выдачи даже имени версии. При подключении нового поля нужно согласовать бюджет ожидания.
- Отдельный дефект подбора версии для устройства: отсутствие ответа о минимальной iOS считается несовместимостью и двигает бинарный поиск к старым сборкам. Также алгоритм полагается на монотонное повышение минимальной iOS, которое не обеспечивается кодом или форматом IPA. Замена источника данных сама по себе эту логику не исправит.

## Рекомендуемая интеграция

1. Сначала кэш Signum.
2. Сохранять minimumOSVersion из уже выполняемых запросов ipatool metadata, сверяя externalVersionID и платформу; success=true без поля не означает известную минимальную iOS.
3. Для ещё неизвестных сборок использовать ipatool 1.2.0; выполнять команды последовательно под существующим ipatool_lock, поскольку они пишут общий cookie-файл. Нативный reader оставить резервным и устранить его ограничения ZIP64/заголовков, если он сохраняется.
4. Сетевую ошибку оставлять как «не удалось определить», без отрицательного кэширования и без объявления сборки несовместимой. У подбора подходящей версии должна быть отдельная обработка неизвестного результата.

## Реализованная интеграция

По следующему запросу пользователя основной источник переключён на ipatool, нативный reader Signum сохранён резервным. Порядок: положительный кэш точной сборки → ipatool get-version-metadata → Signum version_min_ios. В существующий кэш записывается только корректная числовая версия; отсутствие результата не кэшируется.

Парсер требует success=true и совпадение externalVersionID. Если supportedPlatforms указан, среди платформ должен быть iPhoneOS. Поле minimumOSVersion может отсутствовать даже при успешной команде — это включает резерв. Данные минимальной iOS из запросов маркетинговых меток теперь сохраняются, а список версий перечитывает кэш после этих запросов.

Для отдельного чтения минимальной iOS задан таймаут 180 секунд, учитывающий несколько диапазонных запросов upstream. Короткий бюджет меток оставлен отдельно, чтобы список версий не ожидал завершения всех сетевых проверок. CLI вызывается последовательно под ipatool_lock; блокировка освобождается между сборками страницы. Каждый готовый результат отправляется в интерфейс.

Подбор версии для устройства использует тот же основной и резервный источник. Убрана обязательная доступность нативного helper для начала подбора. Неизвестная минимальная iOS больше не продвигает поиск к старым версиям как будто сборка несовместима: пользователь получает сообщение с возможностью повторить подбор или выбрать версию вручную.

Регрессионные тесты покрывают соответствие сборке и платформе, отсутствующее/повреждённое поле, приоритет ipatool, резерв при неуспехе и отсутствие ложной несовместимости. `cargo test --manifest-path src-tauri/Cargo.toml --bin signum -- --test-threads=2`: 133 теста пройдено, 0 ошибок, 2 теста с живым Apple ID штатно пропущены. `git diff --check` не нашёл ошибок пробелов. Реальные запросы к Apple при этой интеграции не выполнялись.

Алгоритм подбора по-прежнему использует бинарный поиск с прежним допущением о порядке требований iOS. Этот отдельный вопрос не менялся в интеграции источников.
